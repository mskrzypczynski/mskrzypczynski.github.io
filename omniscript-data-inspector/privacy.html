Privacy policy — OmniScript Data Inspector

Last updated: 30 October 2026

The short version

This extension collects nothing and sends nothing anywhere of its own. What it stores in your browser is the order of the panel's tabs once you change it, flags that the short tours were seen, the Mask values at start flag if you tick it, and, only if you tick Remember my settings, your panel settings and watch list (never any data), all in the browser's extension storage on this computer. Everything else it holds is kept in memory and is gone when DevTools closes.

It requests one permission, storage, for the entries above, and no access to any website. It has no background service worker, no content scripts, and makes no network requests of its own; the only request it can make is a test call you compose (below). It never changes the OmniScript or its data; the only thing it can do to a running script, on your request, is ask it to show an earlier step again.

What it reads, and when

The extension only does anything while you have Chrome DevTools open and the OmniScript panel in view.

Page data. It reads properties of elements on the page you are inspecting, using the standard chrome.devtools.inspectedWindow API — the same access the DevTools Console already gives you. By default it looks for three properties an OmniScript element exposes: jsonDataStr (the live data payload), jsonDef (the element/structure definition) and scriptHeaderDef (script header, including the custom-label map used to resolve labels in multi-language scripts). You can point the Data property and Definition property fields at any other property name, in which case it reads that instead. To find those elements it walks the document, any open shadow roots, and same-origin iframes.

Network traffic. The Calls tab observes requests the inspected page makes, using chrome.devtools.network. For requests that look like Apex calls it reads the request and response bodies in order to decode the remote action, its input and its output. This is the same traffic already visible to you in the Network tab.

Open in Designer. To offer a link to the OmniStudio Builder or OmniScript Designer, it reads the host elements' tag names, classes and their data-omni-id / omniscript-id attributes, and the page's origin and path (the path only to tell a managed package from core OmniStudio; it is kept in memory and never stored). The choice of designer can be forced in Settings. The link is built in the panel and opened in a new tab only when you click it; nothing is sent. Open record in the Data tab uses the same page origin to build a link to a record whose Id appears in the data, and opens it the same way.

Frames. It asks DevTools which documents are loaded, so it can find an OmniScript inside an iframe such as the OmniScript Designer preview.

Files you choose. When you press Load file… in Compare payloads, it reads the one JSON file you pick from your computer, so it can be compared with the payloads it read. The file is read in the panel and kept in memory only, like the payloads; it is never uploaded or stored.

What it writes to the page. While scanning it sets window.__omniHosts on the inspected page to an array of the elements it found, and window.__omniPeekCache to the parsed copy of the definition it last read, so it does not have to parse it again on every refresh. To avoid copying a large payload over and over, each read of the data property also returns a short hash of the value (FNV-1a, computed on the page) and, when the hash matches what the panel already holds, the page answers "unchanged" instead of sending the text again. The hash is not stored anywhere and the Refresh button always reads the whole value. When you click Inspect element it also sets window.$omni to the selected element and calls the DevTools inspect() helper, so you can poke at it in the Console. When you use Highlight on page (or turn on Highlight on hover) it scrolls the matching element into view and draws a temporary outline over it: a single div with the id __omni_inspector_outline that removes itself after a couple of seconds.

What it sends. Nothing, unless you turn on Allow test calls in Settings (off by default, and never remembered, not even with Remember my settings: it is off at every DevTools start). With it on, Re-run… and New test call… in the Calls tab let you edit the input of a captured Integration Procedure, Data Mapper or Apex call, or of a designer's Preview (a debug run of an Integration Procedure or Data Mapper, sent over Visualforce remoting), and send it again. The panel then makes that one request from inside the inspected page, to the origin of the selected script's own frame, with the page's own session, the same way the page made the original; nothing goes anywhere else, nothing is sent without your pressing Send (Re-run as it was asks every time), and nothing is sent while recording is paused. The answer's text is held in one variable of the page only until the panel has read it, at most a minute, then deleted; the panel keeps at most five such answers in the page at any time. Such a call runs in your org as your user and can create or change records, exactly as the original did. The answer is shown in the panel like any other call and is never written into the script or its data.

When you choose Go to this step or Previous step in the Structure tab, it presses the running script's own Previous button, even when the script hides it, or sends the script the same event that button sends, so the page shows an earlier step again. That changes which step the page shows and nothing else: the script's data is not written, and a script that does not allow going back ignores the request.

All of this stays in the DevTools panel in your browser. It is never transmitted. It is held in memory only. The panel keeps, in memory, the last 12 reads of the data (up to about 4 MB, so two can be compared), and, while Track changes is on, a log of the last 200 values that changed and what they were before, plus any values you chose to watch. None of it is discarded the moment the page navigates or the OmniScript closes: the last data read deliberately stays on screen, marked as stale, so you can still look at it after a script ends or the page reloads. It is replaced when you select another OmniScript or change the Data property field, and everything is discarded when you close DevTools.

What is stored in your browser

Four things, all with chrome.storage.local, the browser's extension storage, on this computer only (it is not synced):

  • The order of the panel's tabs, once you change it (removed again when you put the default order back).
  • Four flags that you have seen the short tours (the panel's and one per tab), written when you close them, so they do not show again (Show the tour again in the help clears them).
  • If you tick Remember my settings in Settings (off by default): the panel's settings (its switches, views, the views you last chose, text size, profile, refresh rate, property names and the designer choice) and your watch list. Of the watch list only the paths and the expressions you typed (including any value you wrote into a comparison), which of them have a bell on, and the script's Type/SubType/Language are kept, for the last 50 scripts, never a value read from the data. Unticking it deletes all of it. Data, filter text, captured calls, payload history and the Mask values switch are never kept.
  • Mask values at start (in Settings, off by default): one yes-or-no flag, kept whether or not Remember my settings is on, that turns the Mask values switch on when DevTools opens. Unticking it deletes it; the switch itself is never stored.

The extension does not use localStorage, sessionStorage, IndexedDB or cookies. Your panel settings (the Advanced switch, the Data view, the refresh rate, property names and the other switches) are held in memory and last until DevTools is closed, unless you tick Remember my settings (see above); Allow test calls is never remembered and is off at every start. The Restore default settings button in Settings, and the Reset next to a single setting there, put settings back without reloading DevTools.

The Calls list is held in memory too. Unless Clear on reload is ticked (it is off by default) the captured calls are kept across page reloads. They are cleared when you close DevTools, when you reload with Clear on reload ticked, or when you press Clear list.

What leaves your machine

Nothing, unless you ask for it.

The Save file, Export and Debug bundle buttons write data to your own disk when you press them (the debug bundle holds the payload and the last payloads read, the current step, the captured calls, what each tab shows, your panel settings and size, the script's definition, Type/SubType/Language and element names, and the extension version; with Mask values on, org data in it is replaced by placeholders, including the answers and defaults the definition carries, and only the script's names and settings stay; a debug run of a designer preview keeps a value-free summary of its steps: names, types, statuses, times and the kinds of its log lines), and the Copy buttons, including Copy as Apex and Copy input, the right-click menu and the copy keyboard shortcut put what you chose on your clipboard. Nothing is uploaded. The Mask values switch (off by default) replaces strings and numbers with placeholders in everything saved, exported or copied, but not in what is shown on screen.

The toolbar popup, the help panel and the panel's status bar offer two Buy me a coffee links, ko-fi.com (EUR, by card) and buycoffee.to (PLN, by card or BLIK), each opening in a new tab only if you click it. Those sites are operated by someone else and have their own privacy policies. No information about you is passed to them by this extension.

Analytics and third parties

There are none. No analytics, no telemetry, no crash reporting, no advertising, no cookies, no user accounts, no third-party services of any kind. No data is sold or shared, because none is collected.

Data you retrieve from your org is your responsibility

This extension is a viewer. It shows you data that is already on the page you are inspecting and that your Salesforce user is already authorised to see. What that data contains, and what happens to it once you look at it, is outside the extension's control and squarely within yours.

Be aware that an OmniScript's data JSON or a captured call can carry personal data, customer records, and internal identifiers. Request payloads may also carry session tokens.

So, concretely:

  • Where you point it matters. Prefer a scratch org, a sandbox, or test records when you are exploring or capturing screenshots. Anything you capture from a production org is production data.
  • Exports and copies are ordinary data. Pressing "Save file" or "Export" writes org data to your disk, and copying puts it on your clipboard, where other applications and clipboard managers can read it. Neither has any protection unless you turned on Mask values first. Where it then goes — a ticket, a chat message, a shared drive, a colleague's laptop — is entirely your decision.
  • Screenshots and screen shares count too. The panel is designed to make data legible, which also makes it legible to whoever is watching your screen.
  • Your own obligations still apply. Your organisation's policies, any confidentiality agreements it is under, and data protection law such as the GDPR govern this data regardless of which tool you viewed it through. Using this extension does not change what you are permitted to do with what you see.

The author provides this tool as-is and accepts no responsibility for how data retrieved through it is handled, stored, or disclosed. This is a plain description of how the tool works, not legal advice — if you handle regulated or confidential data, follow your organisation's guidance.
